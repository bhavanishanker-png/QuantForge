# **4. Critical data and event flows**

This section is particularly important because the technologies must work together correctly.

## **4.1 Backtesting workflow**

1. **User submits a backtest**

   React sends a request to NestJS.
2. **Authorization and validation**

   NestJS validates workspace access, strategy version, dataset and configuration.
3. **Persist transaction**

   Create a backtest record and an outbox event in the same PostgreSQL transaction.
4. **Dispatch job**

   A Python dispatch component reads unpublished outbox events and submits Celery tasks to Redis.
5. **Execute computation**

   Celery invokes the Python quantitative engine and VectorBT.
6. **Persist results**

   Save metrics and result metadata in PostgreSQL; save larger artifacts in MinIO/S3.
7. **Notify frontend**

   Update the persistent job status and publish Socket.IO updates.
8. **Display report**

   React retrieves actual results and displays the equity curve, trades and performance statistics.

### **Important event-dispatch design**

There is a technical integration detail we should explicitly account for:

NestJS should not be expected to publish Celery's internal task protocol directly.

Instead:

1. NestJS creates the job and outbox record.
2. A Python dispatcher claims pending outbox events.
3. The dispatcher publishes the corresponding Celery task.
4. Workers process tasks idempotently.
5. PostgreSQL remains the source of truth.

Use leases, retry counters, unique event IDs and dead-letter handling for events that repeatedly fail.

This avoids coupling the TypeScript application to Celery's internal implementation.

# **5. Quantitative architecture: important correctness rules**

This is the part where I would be especially strict. A trading platform can look impressive while producing misleading backtest results.

## **5.1 Backtesting and execution**

VectorBT is selected for efficient vectorized backtesting. However, vectorization does not automatically guarantee realistic execution simulation.

We should implement a controlled execution and accounting layer around it.

Required rules:

- A signal generated from a completed candle cannot execute at an already-observed closing price.
- Simulated execution should use the next available executable price.
- Account for fees and adverse slippage.
- Use chronological data only.
- Prevent look-ahead bias.
- Track balances, positions, fills and realized/unrealized P&L.
- Make backtests reproducible.

Initial assumptions:

| Setting              | Value         |
| -------------------- | ------------- |
| Market               | Crypto spot   |
| Direction            | Long-only     |
| Commission           | 0.05%         |
| Adverse slippage     | 0.05%         |
| Starting market      | BTC/USDT      |
| Live order execution | Not supported |

## **5.2 Financial precision**

Use two different numeric approaches for different jobs.

| Use case                 | Numeric representation |
| ------------------------ | ---------------------- |
| Balances                 | Decimal / NUMERIC      |
| Orders and fills         | Decimal / NUMERIC      |
| Fees                     | Decimal / NUMERIC      |
| Accounting and P&L       | Decimal / NUMERIC      |
| Indicators               | NumPy Float64          |
| Vectorized research      | NumPy Float64          |
| Statistical calculations | NumPy Float64          |

Conversions between these representations must be explicit.

For virtual trading, financial updates should use database transactions, constraints, idempotency keys and unique fill identifiers.

## **5.3 Optimization correctness**

Scikit-learn SearchCV is selected, but its standard estimators are not directly a strategy-optimization framework.

Create a strategy-evaluation adapter compatible with the SearchCV interface.

Use:

- TimeSeriesSplit or other chronological validation.
- No shuffled random cross-validation.
- A separate final holdout dataset.
- Walk-forward validation.
- Parameter sensitivity analysis.
- Transaction-cost stress testing.

Do not select strategies solely because they perform well on the data used to optimize them.

## **5.4 Strategy security**

Custom Python strategy execution must never run inside the NestJS or FastAPI application process.

Use isolated execution containers with:

- Non-root execution.
- CPU and memory limits.
- Execution timeouts.
- Restricted filesystem access.
- Restricted network access.
- No application secrets.
- Explicit input/output schemas.

Docker containers alone should not be treated as a complete security boundary for malicious multi-tenant code. Stronger isolation such as gVisor or Firecracker can be considered later.

## **6.2 Important database rules**

1. Use UUID primary keys.
2. Use UTC timestamps.
3. Use NUMERIC for financial values.
4. Add workspace IDs to workspace-owned records.
5. Enforce workspace isolation through RLS and application authorization.
6. Use foreign keys and unique constraints.
7. Index frequently queried columns.
8. Partition historical candle data by time.
9. Keep strategy versions immutable.
10. Keep completed experiment records reproducible.

### **Backtest reproducibility**

A backtest must preserve:

- Strategy version ID.
- Dataset ID and checksum.
- Instrument and timeframe.
- Start and end dates.
- Parameter configuration.
- Initial capital.
- Commission and slippage.
- Execution assumptions.
- Engine version.
- Metrics, trades and equity curve.
- Completion status and timestamps.

A user should be able to inspect an old experiment without relying on the current version of their strategy or current market data.

## **6.3 PostgreSQL RLS and PgBouncer**

This deserves special implementation attention.

Since PgBouncer transaction pooling is selected, workspace context must be set inside the database transaction.

For example, use a transaction-local setting:

```
BEGIN;

SET LOCAL app.current_workspace_id = 'workspace-uuid';

-- Workspace-scoped queries

COMMIT;
```

The actual application should establish this context using a trusted, validated workspace identity. Never allow a client to choose arbitrary workspace context without authorization.

Prisma integration with transaction-local RLS context and PgBouncer must be tested explicitly. If a particular operation cannot safely preserve the transaction context, it must use an appropriate transaction-aware connection path.

## **6.4 Data storage boundaries**

**PostgreSQL**

Source of truth

- Users and workspaces.
- Strategies and versions.
- Orders, fills and balances.
- Job status.
- Experiment metadata and metrics.

  **MinIO / S3**
- Parquet datasets.
- Large backtest artifacts.
- Research reports.
- Optimization outputs.

  **Redis**
- Cache.
- Celery broker.
- Socket.IO adapter.
- Rate limiting.
- Temporary coordination data.

Do not store authoritative account balances or completed financial transactions only in Redis.

# **8. API design**

Use versioned REST endpoints for application workflows.

All endpoints should have consistent validation, authorization, error responses and pagination.

| Module          | Main endpoints                                           |
| --------------- | -------------------------------------------------------- |
| Auth            | `/api/v1/auth/register`, `/login`, `/refresh`, `/logout` |
| Workspaces      | `/api/v1/workspaces`                                     |
| Markets         | `/api/v1/markets/instruments`, `/candles`, `/sync`       |
| Strategies      | `/api/v1/strategies`                                     |
| Backtests       | `/api/v1/backtests`                                      |
| Optimization    | `/api/v1/optimizations`                                  |
| Factors         | `/api/v1/factors`                                        |
| Virtual trading | `/api/v1/virtual-accounts`                               |
| AI              | `/api/v1/ai/conversations`                               |
| Jobs            | `/api/v1/jobs`                                           |

For long-running operations, return HTTP `202 Accepted` with a persistent job ID.

Example:

```
{
  "jobId": "uuid",
  "status": "QUEUED",
  "resourceType": "BACKTEST",
  "resourceId": "uuid"
}
```

Do not keep HTTP requests open while running backtests or optimization searches.

**Pagination policy:**

- Offset pagination for users, workspaces and strategies.
- Cursor pagination for candles, trades, orders, jobs and equity points.
- Use stable indexed ordering and composite cursors where needed.

## **11.1 A few non-negotiable safety and correctness rules**

These should become explicit project requirements:

- No live trading or broker order submission in the initial release.
- Virtual trading must use simulated accounts only.
- No API keys or credentials in frontend code.
- No arbitrary SQL execution through MCP.
- No unrestricted Python execution inside application services.
- No fabricated market data or dashboard metrics.
- No backtest results without recorded execution assumptions.
- No random train/test splitting for time-series optimization.
- No financial balances stored only in Redis.
- No cross-workspace access, including through background workers.

## **13. My assessment of the architecture**

Ready for Phase 1 planning

Stack frozen

The architecture is comprehensive, but I would make three recommendations before implementation:

**1. Don't implement every selected technology immediately.**

For example, you don't need EKS, Argo CD, GlitchTip, AWS KMS and the complete monitoring stack to get your first local development environment running.

Create the interfaces and deployment boundaries where appropriate, then introduce the infrastructure in the relevant phase.

**2. Keep the NestJS application as the source of business authorization.**

The Python engine should calculate, validate and execute quantitative workloads. It should not independently invent business permissions or bypass workspace authorization.

**3. Prioritize correctness over the number of features.**

A trustworthy backtest engine, reliable market data and accurate virtual account accounting are more valuable than having ten incomplete modules.
