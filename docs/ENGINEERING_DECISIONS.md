## ADR-001 — Contracts: OpenAPI as the source of truth

**Status:** Accepted (2026-11-14). This supersedes the stack choice "manually maintained shared TypeScript types".

**Context.** The system spans three languages (React/TS, NestJS/TS, Python). Keeping types in sync by
hand across them drifts silently.

**Decision.**
- **Public API (NestJS → web, MCP):** NestJS DTOs with `@nestjs/swagger` decorators produce
  `openapi.json`. `packages/api-client` generates TS types from it with `openapi-typescript`, plus a
  thin typed fetch wrapper (`openapi-fetch`). The web app and the MCP server import only from there.
- **Internal API (NestJS → FastAPI):** FastAPI's own OpenAPI spec (from Pydantic models) generates
  TS types for the NestJS client in the same way.
- **Job payloads (outbox events → Celery):** one JSON Schema per event type lives in
  `packages/contracts/events/*.schema.json`. Python validates with Pydantic models (generated by
  `datamodel-code-generator` or written by hand and checked against the schema in CI). TS validates with Zod.
- **CI gate:** regenerate everything and run `git diff --exit-code`. Stale generated code fails the build.

**Consequences.** Clients never hand-write API types. An API change becomes a single diff to the DTO,
and the regenerated client shows exactly what changed.

## ADR-002 — Workspace isolation: RLS through Prisma and PgBouncer

**Status:** Proposed. Spike 1 (`spikes/rls-prisma-pgbouncer`) validates it.

**Context.** RLS depends on a per-request `app.current_workspace_id`. In transaction pooling mode,
PgBouncer may hand each statement to a different server connection unless the statements share a
transaction. Session-level `SET` would leak between tenants. Only `SET LOCAL` / `set_config(..., true)`
inside a transaction is safe.

**Decision.**
1. **Three database roles:**
   - `qf_migrator`: owns the tables and runs Prisma Migrate. Because of `FORCE ROW LEVEL SECURITY`
     it is **also subject to RLS** (verified in spike 1: the owner sees 0 rows with no context). This is
     intended. A data backfill inside a migration must set the context explicitly.
   - `qf_app`: NestJS uses it. `NOBYPASSRLS`, with DML grants only.
   - `qf_worker`: Python workers use it. `NOBYPASSRLS`. Grants are limited to the tables workers write to.
   - `qf_dispatcher`: the outbox dispatcher and reaper use it. It may access only `outbox_events` and `background_jobs`.
   - (Later) `qf_admin_readonly` for operations. It bypasses RLS and every use is audited.
2. **Policies** apply to every table that has a `workspace_id`, with `FORCE ROW LEVEL SECURITY`:
   ```sql
   USING (workspace_id = current_setting('app.current_workspace_id', true)::uuid)
   WITH CHECK (workspace_id = current_setting('app.current_workspace_id', true)::uuid)
   ```
   When the setting is missing, the comparison yields NULL, so no rows match (fail closed).
3. **NestJS:** a `WorkspaceScopedPrisma` service exposes `withWorkspace(workspaceId, fn)`. It runs
   `fn` inside `prisma.$transaction(async tx => { await tx.$executeRaw\`SELECT set_config('app.current_workspace_id', ${id}, true)\`; return fn(tx); })`.
   Repositories for workspace-owned data accept only the `tx`, never the root client. A lint rule
   bans importing the root `PrismaClient` outside `common/database`.
4. **Trust:** the workspace ID comes from the `X-Workspace-Id` header and is checked against
   `workspace_members` for the authenticated user before `withWorkspace` runs. The membership check
   runs against tables that are not RLS-scoped (`users` and `workspace_members` use their own
   user-based policy).
5. **Python workers:** each job carries `workspace_id`. The worker opens one SQLAlchemy transaction
   per unit of work and runs the same `set_config` as its first statement.
6. **Prisma 7 uses the `@prisma/adapter-pg` driver adapter** (node-pg, unnamed statements) through
   PgBouncer, which runs with `max_prepared_statements = 0`. Migrations bypass PgBouncer and connect
   directly to Postgres as `qf_migrator`.
7. **PgBouncer resets every server connection after every transaction:**
   `server_reset_query = RESET ALL` plus `server_reset_query_always = 1`. Without it, spike 1 showed
   that a stray session-level `SET app.current_workspace_id` persists on the pooled connection, and
   later queries **without** a context from *other clients* inherit it, so RLS **fails open**. The
   measured overhead is negligible (400 concurrent transactions on a 3-connection pool: about 725 ms
   either way).
8. **CI lint:** fail the build on any `SET app.` or `set_config('app.…', …, false)` outside
   `common/database`. A session-level set is always a bug.

**Validated by spike 1 (2026-11-14, `spikes/rls-prisma-pgbouncer`, 7/7 passing):**
a workspace sees only its own rows. With no context, queries return zero rows. Inserts into another
workspace fail `WITH CHECK`. Updates and deletes against another workspace affect 0 rows. The context
does not survive past its transaction. 400 concurrent mixed-tenant transactions through a
3-connection pool never cross. A stray session `SET` does not leak (regression guard for item 7).

**Status:** Accepted (2026-11-14).

## ADR-003 — Database write ownership between NestJS and Python

**Status:** Accepted (2026-11-14)

- Prisma owns the **schema and all migrations**. Python never runs DDL, and there is no Alembic.
- **NestJS writes:** identity, workspaces, strategies and versions, run *requests* (`backtest_runs`
  in `QUEUED`), `background_jobs`, `outbox_events`, virtual-account configuration.
- **Python writes:** computed results (`backtest_trades`, `backtest_equity_points`,
  `backtest_metrics`, optimization trials, factor results, candles, virtual fills during forward
  runs), plus job status transitions to `RUNNING`, `COMPLETED` and `FAILED`.
- Python uses **SQLAlchemy Core** `Table` definitions in `quant-engine/app/db/tables.py`. A CI test
  reflects the migrated database and fails if any column the Python side declares is missing or has
  a different type.

## ADR-004 — Real-time updates: Redis pub/sub to Socket.IO

**Status:** Proposed. Spike 2 validates it.

**Decision.**
- After committing a state change, a worker publishes a small event to Redis channel
  `qf:events:{workspaceId}`: `{type: "job.updated", jobId, status, progress, ts}`.
- NestJS pattern-subscribes to `qf:events:*` and emits to the Socket.IO room `workspace:{id}`.
  Socket connections authenticate with the access token, and joining a room requires membership.
- The frontend treats each event as an **invalidation signal** and refetches through TanStack Query.
  Postgres stays the source of truth, so a missed pub/sub message only delays the UI. A reconnect
  triggers a full refetch.
- Live market candles use the same path on channel `qf:market:{exchange}:{symbol}:{tf}`.

**Validated by spike 2.** Events reach only their workspace's room. **Status:** Accepted (2026-11-14).
Still to build in Phase 1: JWT authentication in the socket handshake and the membership check on `workspace.join`.

## ADR-005 — Transactional outbox and job lifecycle semantics

**Status:** Proposed. Spike 2 validates it.

**Tables.** `background_jobs` (the persistent job record) and `outbox_events` (dispatch intents).
NestJS inserts both in **one transaction** together with the domain row (for example a `backtest_runs` row).

**Dispatcher** (`quant-engine/workers/outbox_dispatcher`, Python):
- Polls every 500 ms, and also wakes on `LISTEN outbox_new` (NestJS sends `NOTIFY` after commit).
- Claims a batch:
  ```sql
  UPDATE outbox_events SET status='CLAIMED', claimed_until=now()+interval '60 seconds', attempts=attempts+1
  WHERE id IN (SELECT id FROM outbox_events
               WHERE status='PENDING' OR (status='CLAIMED' AND claimed_until < now())
               ORDER BY created_at LIMIT 50 FOR UPDATE SKIP LOCKED)
  RETURNING *;
  ```
- Publishes with `celery.send_task(name, args=[payload], task_id=str(event.id), queue=route)`, then
  marks the event `PUBLISHED`. A crash between the publish and the mark causes a re-publish with the
  same task ID, and the worker's idempotency check absorbs it.
- If `attempts >= 5`, the event moves to `DEAD`, the job is set to `FAILED` with `error_code=DISPATCH_FAILED`,
  and an audit event is written.

**Workers:**
- `acks_late=True`, `reject_on_worker_lost=True`, `task_acks_on_failure_or_timeout=True`, plus a
  per-queue `time_limit`.
- **Idempotent start:** `UPDATE background_jobs SET status='RUNNING', attempt=attempt+1, heartbeat_at=now(), started_at=coalesce(started_at, now()) WHERE id=$1 AND status IN ('QUEUED','RUNNING') AND (status='QUEUED' OR heartbeat_at < now()-interval '90 seconds') RETURNING *`.
  If no row comes back, another worker owns the job or it already finished, so the task exits without doing anything.
- Workers update `heartbeat_at` every 15 s while running.
- Result writes for a job are idempotent: each run deletes and re-inserts its result rows inside the
  completing transaction, keyed by `run_id`.
- Cancellation: the API sets `cancel_requested=true`. Workers check it on every heartbeat and finish as `CANCELLED`.

**Fencing:** every write after the claim (heartbeat, completion, result rows) is conditional on
`status='RUNNING' AND attempt = <the claimed attempt>`. If that check fails, the worker has lost
ownership and abandons the job. The business effect and the terminal status commit in **one transaction**.
Everything after the claim runs inside the task's error handler, so any exception ends the job as
`FAILED` with `TASK_ERROR` at once instead of waiting for the reaper.

**Reaper** (runs **inside the dispatcher process**, every 30 s, *not* as a Celery Beat task, because
a Beat-scheduled reaper runs on a worker and stops when all workers are dead):
- `RUNNING` with a heartbeat older than 90 s and `attempt < max_attempts` → back to `QUEUED`, with a new outbox event.
- The same, with `attempt >= max_attempts` → `FAILED` with `error_code=WORKER_LOST`.
- `QUEUED` whose outbox event has been `PUBLISHED` for more than 10 minutes without a claim (the message was lost, e.g. Redis data loss) → a new outbox event. *(To be added in Phase 1.)*

No job stays in `RUNNING` indefinitely. Terminal states are enforced by a trigger.

**States:** `QUEUED → RUNNING → COMPLETED | FAILED | CANCELLED`. Terminal states never change.

**Validated by spike 2 (2026-11-14, `spikes/job-pipeline`, 10/10 passing, twice in a row):**
the happy path with live Socket.IO updates; workspace room isolation; duplicate delivery producing no
second effect; 100 concurrent jobs each exactly once; cancellation; dead-letter after 5 dispatch
attempts; a SIGKILLed worker reaped with zero workers alive and completing on attempt 2 with one effect;
`WORKER_LOST` after max attempts; immediate `TASK_ERROR`; a zombie worker fenced out.

**Status:** Accepted (2026-11-14).

## ADR-006 — Two Redis instances

**Status:** Accepted (2026-11-14)

`maxmemory-policy` applies to a whole Redis instance, not to one logical DB, and a broker that
evicts keys loses tasks. So:
- `redis-queue`: `noeviction`, AOF `everysec`. Holds the Celery broker, the result backend (if used) and pub/sub.
- `redis-cache`: `allkeys-lru`, no persistence. Holds the application cache, rate-limiter counters
  and the Socket.IO adapter.

Locally both run from the same `redis:7` image as two Compose services.

## ADR-007 — Authentication token model

**Status:** Accepted (2026-11-14)

- Passwords: Argon2id (`argon2` npm), m=19456 KiB, t=2, p=1 (OWASP baseline).
- **Access token:** a 15-minute JWT (HS256 in v1, EdDSA later), with claims `sub` and `sid` (session ID).
  It carries **no** workspace or role claims: those are resolved per request, so revoking a membership takes effect immediately.
  The SPA keeps it **in memory only**.
- **Refresh token:** an opaque 256-bit random value in an `httpOnly; Secure; SameSite=Strict` cookie scoped to
  `/api/v1/auth`. Only its SHA-256 hash is stored in `refresh_tokens`, together with `family_id`.
  Each refresh rotates the token. **Reuse detection:** if a revoked token is presented, the whole family is revoked.
- Workspace context: the `X-Workspace-Id` header is checked against membership on every request (ADR-002).
- Rate limits: login and register allow 10 requests per minute per IP and per email, using Redis-backed Throttler storage.

## ADR-009 — Primary exchange: Binance

**Status:** Accepted (2026-11-14)

- Binance spot through CCXT for historical OHLCV, and the native Binance WebSocket kline streams for live candles.
- Every exchange sits behind an `ExchangeAdapter` interface that exposes `capabilities()` (timeframes,
  history depth, rate limits). v1 enables only Binance, but the interface is designed with a second
  adapter in mind (Bybit or OKX) as a fallback if Binance is unreachable.
- Public market data only. No API keys are needed in v1.
- **Risk:** Binance.com is unreachable from some jurisdictions. The adapter's health check reports this clearly instead of failing silently.

## ADR-010 — Candle storage and dataset snapshots

**Status:** Proposed

- `market_candles(instrument_id, timeframe, open_time, open, high, low, close, volume, is_closed, ingested_at)`.
  The primary key is `(instrument_id, timeframe, open_time)`. Prices and volume are stored as `NUMERIC`.
  The table is range-partitioned by `open_time`, one partition per month, created with handwritten SQL in a Prisma migration.
- Native timeframes are ingested as the exchange supports them. A validation job checks higher
  timeframes against 1m data resampled to the same interval and reports any mismatch.
- Only the current open candle has `is_closed = false`. The historical sync never writes an open candle.
- **Dataset snapshot:** when a backtest is submitted, a worker exports the exact candle range to
  Parquet, computes a SHA-256 checksum and records it in `datasets(id, instrument_id, timeframe, start, end, row_count, checksum, uri)`.
  The backtest then references `dataset_id`, which makes it reproducible even if candles change later.

## ADR-011 — Strategy modes in v1

**Status:** Proposed

v1 ships **built-in strategies** (SMA crossover, EMA crossover, RSI threshold, MACD crossover,
Bollinger Bands) and a **JSON rule DSL** (indicator, comparison, threshold, AND/OR) validated by a
JSON Schema and by the Python engine. The visual builder (it emits the same DSL) and **sandboxed
Python** (`on_bar` API, gVisor/Firecracker isolation) stay behind feature flags until after v0.1.

## ADR-012 — Backtest engine: VectorBT behind an interface

**Status:** Proposed

- The open-source `vectorbt` package is pinned. It receives only maintenance updates, and PRO is a
  separate commercial product. All use goes through a `BacktestEngine` protocol so the engine can be replaced later.
- Execution rule: signals are computed on closed bar *t* and filled at the **open of bar t+1**, adjusted
  by adverse slippage. Commission is 0.05% and slippage is 0.05%. Long-only spot. No position on the final bar is
  left open silently: it is either marked to market or closed, as the config specifies.
- Accounting converts float64 engine output to `Decimal` at the boundary. Fills are re-derived in Decimal
  and checked against the engine's own figures (tolerance 1e-8 relative).
- Required tests: a golden dataset with hand-computed trades, and a look-ahead test in which a
  strategy that peeks at the future must show no edge under the engine's execution rule.

## ADR-013 — Metric conventions

**Status:** Proposed

Periods per year = 365 × bars per day (crypto trades 24/7). Risk-free rate = 0. Sharpe and Sortino use
bar-level returns of the equity curve. Max drawdown is computed on equity at each bar's close. CAGR uses
calendar time. Every metric's definition is written in `docs/METRICS.md` and covered by a test.

## ADR-014 — Forward simulation runner

**Status:** Proposed

A virtual account runs a strategy version **on each candle close** for its timeframe, triggered by the
live-candle pipeline. The runner calls the same signal function as the backtester. A parity test runs
the same bars through both and requires identical trades. Market and limit orders only. Fills carry
a unique `(account_id, signal_bar_time, strategy_version_id)` idempotency key.

## ADR-015 — Optimization implementation

**Status:** Proposed

The standard choice is a `StrategyEstimator` that implements the scikit-learn `fit`/`score` interface,
so `GridSearchCV` and `RandomizedSearchCV` can run with `cv=TimeSeriesSplit(gap=...)`. The simpler
alternative, still within scikit-learn, uses `ParameterGrid`/`ParameterSampler` directly with our own
walk-forward loop. **Recommendation:** pick the simpler option unless the SearchCV object itself is
needed. In every case the final holdout is never touched during the search. The deflated Sharpe ratio
and parameter-sensitivity heatmaps are reported.

## ADR-016 — Factor Lab universe

**Status:** Proposed

Cross-sectional IC across 3 instruments is statistically meaningless. Before Phase 7, the universe
grows to the top ~50 USDT spot pairs by volume, with survivorship-aware listing dates, or Phase 7 v1
is limited to time-series IC. Benjamini–Hochberg FDR control applies across all evaluated factors.

## ADR-017 — AI runtime and MCP

**Status:** Proposed

LangGraph.js runs inside the NestJS `ai` module, so it shares auth and services. The MCP server is
TypeScript and calls the public API using a token scoped to one workspace. Tools are split into
**read** and **action** sets, and every action tool requires explicit user confirmation. Each
workspace has a token and cost budget. Each answer cites the IDs of the records it used.

## ADR-018 — Credential encryption key hierarchy

**Status:** Deferred to Phase 9. v1 stores no exchange credentials because it uses public data only.

## ADR-019 — Open-source license

**Status:** Deferred to Phase 9. The options are Apache-2.0 (adoption) or AGPL-3.0 (protection against hosted forks).
